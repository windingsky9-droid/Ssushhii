API engineering

Safe API integrations are mostly boundary design.

Practical notes for small Python and web projects.

A reliable integration begins by separating the browser from private credentials. The client should call your server, and your server should call the provider. That one boundary prevents a large class of accidental leaks.

Keep secrets out of the client

Environment variables and deployment secrets belong on the server. Never bake a production token into browser JavaScript, committed source, screenshots, or example configuration.

Wrap providers behind a stable interface

Create one small adapter per provider. The rest of the application should depend on your own functions and data shapes rather than a vendor-specific response object.

Useful rule: if changing vendors requires editing UI code everywhere, the provider boundary is too weak.

Make failure states boring

Handle timeouts, rate limits, malformed responses, and authentication errors explicitly. Return a predictable application error instead of letting raw provider exceptions leak into the interface.

Test the unhappy path

Mock successful responses, empty responses, slow responses, and provider failures. A production integration is defined as much by its error behavior as by its happy path.
